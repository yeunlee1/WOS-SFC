## 1. 배경과 목표

채팅 자동번역은 지금 클라이언트마다 외국어 메시지를 하나씩 `POST /translate`로 요청하고, 서버가 Anthropic Haiku에 "번역해라" 한 줄 프롬프트로 호출한다. 2026-09-09 실측(`클로드 출력물/2026-09-09-wos-오케스트레이션/번역-실측-2026-09-09.md`)에서 게임 용어 24개 중 6개가 틀렸고(창병→spearmen, 화로→Hwaro, 사수→archer 등), 클라이언트 큐가 6.5초에 한 건씩만 번역해 분당 30건 규모를 못 따라가며(감사 C-1), 서버 전역 한도 60/분이 언어 3방향 × 30건에 못 미친다(C-2). 발신 언어(계정)와 번역 대상 언어(UI)의 근원이 달라 번역이 조용히 빠지는 경우가 있다(C-6). 로컬 개발 환경에는 번역 키가 없어 조용히 실패한다.

목표.

1. 공급자를 OpenAI로 바꾸고 **가성비 모델**을 실측으로 고른다(기본 gpt-5.4-mini).
2. **WOS 용어**가 ko·en·ja·zh·ru 모든 방향에서 일관되게 번역된다.
3. **토큰과 호출 수를 최소화**한다 — 메시지 1건당 API 호출 1회, 프롬프트는 문장에 등장한 용어만 주입.
4. 번역이 **원활**하다 — 메시지 도착 후 1~2초 안에 번역이 모든 접속자에게 도착하고, 히스토리는 접속 즉시 번역돼 보인다.
5. 채팅의 **견고성** — 저장 실패 즉시 ack, 입퇴장 폭주 제거, 언어 오설정에 강함, 실패가 보인다.
6. 채팅 UI/UX를 현재 테마 3종(frost·spring·daylight) 안에서 개선한다 — 번역 상태 표시, 실패 표시, 375px, 중복 코드 제거.

비목표. 새 UI 시안, `ru` 전체 UI 문구 추가(UI는 en 폴백, 번역 대상으로는 완전 지원), Anthropic 병행 운영, 게시글 번역의 구조 변경(단건 엔드포인트 유지), 메시지 페이지네이션.

사용자 결정(2026-09-09). 검증 통과한 PR은 야간에 병합한다. 디자인은 테마 3종 안에서 개선. 언어 `other` 사용자는 **영어** 번역을 받는다. 용어집 초안 그대로 쓰고 아침에 검토한다.

## 2. 현재 구조 (2026-09-10 master aa4d2c0 기준 사실 — 감사 C 2·3절이 파일:줄로 확정)

- 서버. `ChatGateway.handleMessage`가 저장 후 `chat:message`를 브로드캐스트. 번역은 `TranslateController`(`POST /translate`, DB 캐시 + 진행 중 요청 공유 + 한도 60/10/60 per min) → `TranslateService`(Anthropic, `claude-haiku-4-5-20251001`, 30초·재시도 0). 캐시 키 `translate:{lang}:sha256(version\0lang\0text)`, 테이블 `translations(cache_key, translated, updated_at)`. 원문 언어는 키에 없다.
- 웹. `useSocket.js`의 큐가 메시지마다 `translateChatMessage` → `api.translate`. 6.5초 간격, 3회 재시도, 429는 최대 5회, 40초 타임아웃. 결과는 `translatedContent`·`translatedLanguage`에 저장. localStorage 캐시 500건(키에 공급자 버전 없음, C-10). `ChatTab`·`ChatDock`가 각자 메시지 컴포넌트를 갖는다.
- 언어. 사용자 `language ∈ ko,en,ja,zh,ru,other`(계정, 바꾸는 API 없음). 번역 대상 = UI 언어(`localStorage wos-lang`, 헤더 셀렉트는 ko/en/ja/zh만). 발신 메시지의 `language`는 소켓 접속 시점의 계정 언어.
- 결함(감사 C 확정). 저장 예외 시 ack 부재로 웹이 5초 뒤 실패 표시(C-4). 입퇴장 `chat:system`이 코얼레싱 없이 전체 방송(N² 패킷, C-5). 스토어 상한(500)에서 밀린 메시지도 번역 요청(C-3). 캐시 저장 실패가 요청 전체 실패로(C-8). 웹 캐시 버전 부재(C-10). 죽은 엔드포인트 `GET /translations/:key`(C-12). 계약 경계 테스트 공백(C-13).
- 키. `OPENAI_API_KEY`가 `server/.env`와 루트 `.env`에 있다(gitignore). Docker compose는 아직 전달하지 않는다.

## 3. 새 구조

### 3.1 언어의 근원 — 대상 언어는 클라이언트가 보고한다 (C 5절 A·E)

- 웹은 소켓 접속 직후와 UI 언어·자동번역 토글이 바뀔 때마다 `chat:language { lang: 'ko'|'en'|'ja'|'zh'|'ru' | null }`을 보낸다. `null`은 자동번역 꺼짐. 값은 `effectiveLang(UI 언어)` — `other`·미지 값은 `en`.
- 서버 `ChatGateway`는 소켓별 `targetLang`을 유지한다(`connectedUsers`에 필드 추가). 보고가 오기 전 초기값은 `effectiveLang(계정 언어)`.
- 접속자 언어 집합 `onlineTargetLangs()` = 소켓별 `targetLang` 중 null 아닌 값의 집합.
- 원문 언어는 **선언값을 믿지 않는다.** 스크립트 판별(3.4)로 확실한 경우만 대상에서 빼고, 모델이 `source`를 돌려준다(3.3). 계정 언어는 표시용 힌트로만 남긴다.

### 3.2 메시지 흐름 — 서버 푸시 번역

1. `chat:message` 수신 → 검증·한도 → **저장**(try/catch — 예외면 `{ ok:false, reason:'failed' }` 즉시 ack, C-4) → 즉시 `chat:message` 브로드캐스트(현행 순서 유지, id 확보 후 방송, C 5절 C).
2. 게이트웨이가 `ChatTranslationService.enqueue(message)`를 **await 없이** 호출한다. 서비스는 전역 번역 큐(동시 실행 최대 4, 분당 `TRANSLATE_GLOBAL_RPM` 상한)에 넣는다(N).
3. 대상 언어 집합 = `onlineTargetLangs()` − `unambiguousScript(text)`가 가리키는 언어(3.4). 대상이 비면 `chat:translation { id, translations: {} }`를 방송하고 끝(O — 웹이 폴백 타이머를 걸지 않게).
4. `message_translations`(3.6)에 이미 있는 언어는 빼고, 남은 언어를 **한 번의 OpenAI 호출**로 번역한다(3.3). 출력 토큰 상한을 길이·대상 수로 계산하고, 상한(1500)을 넘으면 언어별로 나눠 호출한다(J).
5. 결과를 `message_translations`에 저장하고 `chat:translation { id, translations: { [lang]: string } }`를 전체에 방송한다(기존 저장분 포함).
6. 실패(공급자 오류·한도 초과·JSON 파손)는 `chat:translation { id, translations: {기존분}, failed: [lang...], error: 'provider'|'limit' }`로 방송한다(G). 웹은 15초 뒤 배치 폴백 1회.

### 3.3 번역 엔진 (`server/src/translate/`)

- SDK. 공식 `openai` npm, `client.responses.create`. `reasoning: { effort: 'none' }`, `text: { verbosity: 'low' }`, `text.format = json_schema(strict)`, `store: false`, 타임아웃 30초, 자동 재시도 0. `temperature` 없음.
- `max_output_tokens = min(1500, targets × ceil(len(text) × 2.5) + 100)`. 1500을 넘으면 대상 언어를 나눠 호출(J).
- 모델. 환경변수 `TRANSLATE_MODEL`, 기본 `gpt-5.4-mini`. 평가 스크립트(3.10)로 `gpt-5.4-nano`, `gpt-5.6-luna`, `gpt-4.1-nano`, `gpt-4.1-mini`, `gpt-5-nano`를 같은 세트로 돌려 **모든 언어 방향에서 용어 100%·오출력 0**인 가장 싼 모델이 있으면 기본값을 그것으로 바꾸고 근거를 PR에 적는다. 실측 기준 luna는 한국어 방향에서 영어를 섞어 탈락했다.
- 프롬프트(개발자 지시, 약 80토큰 + 용어 행). 역할 한 줄, 규칙(번역문만, 채팅체로 짧게, 숫자·시각·좌표·닉네임·연맹 태그 그대로, **반드시 대상 언어로만 쓰고 원문 언어 단어를 남기지 말 것**, 원문이 이미 그 대상 언어면 그대로 돌려줄 것, `source`에 감지한 원문 언어 코드), 그 뒤에 **선택 주입된 용어 행**. 입력은 `{"targets":["en","ja"],"text":"..."}` JSON 한 줄.
- 출력 스키마. 단건 `{ "source": "ko"|"en"|"ja"|"zh"|"ru"|"unknown", "en": string, "ja": string }`(대상 언어 키만, `additionalProperties: false`). 배치 `{ "items": [ { "id": string, "source": ..., "text": string } ] }`.
- 용어집 선택 주입. `glossary.ts`에 행 배열 `{ ko, en, ja, zh, ru: string[] }`(첫 원소가 대표 표기, 나머지 별칭). 원문에서 어느 열의 별칭이든 등장하면 그 행을 `{매칭 표기}={대상 언어 대표 표기|...}`로 넣는다. 라틴·키릴은 대소문자 무시·단어 경계, 한 글자 한국어(`성`)는 조사·공백 경계에서만. 최대 12행.
- 캐시. 채팅은 `message_translations(message_id, lang)` 테이블(3.6)이 곧 캐시다 — 히스토리 조인·유실 복구가 싸고 원문 언어 모호성(I)이 없다. 게시글 단건은 기존 텍스트 해시 캐시를 유지하되 키 버전을 `openai:{model}:v2`로 올린다. 메모리 LRU(2000건, 30분)는 단건 경로에만 둔다.
- 캐시 저장 실패는 로그만 남기고 번역문은 돌려준다(C-8).
- 사용량 로그. 호출마다 `input_tokens`, `cached_tokens`, `output_tokens`, 대상 언어 수, 소요 ms를 로그로 남기고 누적 카운터를 `GET /translate/usage`(developer)로 노출.
- 프롬프트 캐시. OpenAI는 1024토큰 미만 접두어를 캐시하지 않는다. 우리 프롬프트는 100~250토큰이라 캐시를 기대하지 않고 **짧게 유지하는 것**이 전략이다.

### 3.4 스크립트 판별 — "건너뛰기"에만 쓴다 (F)

- `detectScript(text)` → `ko|ja|ru|han|latin|mixed|none`. 규칙 — 글자(letter)가 0이면 `none`. 한글만(다른 스크립트 글자 0)이면 `ko`. 가나가 있으면 `ja`. 키릴만이면 `ru`. 한자만이면 `han`(ja/zh 구분 불가). 라틴만이면 `latin`(en이라고 단정하지 않음). 둘 이상 섞이면 `mixed`.
- `unambiguousLang(text)` → `ko|ja|ru|null`. 이 값이 있을 때만 그 언어를 대상에서 뺀다. `none`이면 모든 언어를 건너뛴다(번역 불필요). `han`·`latin`·`mixed`는 아무것도 빼지 않는다(모델이 `source`로 판단, 이미 그 언어면 원문 그대로 반환).
- 웹도 같은 규칙(`web/src/chat/script.js`)으로 배치 후보를 줄인다. 테스트 픽스처 6종(숫자·좌표·이모지, 혼합, 한자 전용, 로마자 한국어, 독일어, 키릴)을 서버·웹이 공유한다(3.9).

### 3.5 히스토리와 배치 (D·H·K·L)

- `chat:history`는 `messages LEFT JOIN message_translations`로 조회해 항목마다 `translations: { [lang]: string }`(없으면 `{}`)을 싣는다. 쿼리 1회.
- 웹은 히스토리 중 내 언어 번역이 없고 `unambiguousLang ≠ 내 언어`인 항목을 **최신 50건만** 먼저 배치로 요청하고, 그보다 오래된 항목은 사용자가 위로 스크롤해 화면에 들어올 때(IntersectionObserver) 20건씩 요청한다.
- `POST /translate/batch` 요청 `{ targetLang, items: [{ id: number, text: string }] }` — 항목 ≤20 **그리고** 원문 합 ≤2000자. DTO는 중첩 검증(`@ValidateNested({ each: true }) @Type(() => …)`, `@ArrayMaxSize(20)`, `@IsInt` id, `@MaxLength(500)` text). 응답 `{ translated: { [id]: string }, skipped: number[], failed: number[] }` — `skipped`는 이미 그 언어라 번역 불필요, `failed`는 공급자 실패. 서버는 `message_translations`에 있는 항목을 먼저 채우고 미스만 한 번의 호출로 번역, 저장한다. JSON 파손 시 항목 단위로 1회 재시도, 그래도 실패면 `failed`.
- 웹은 `failed`만 10초·30초 뒤 2회 재시도하고 그 뒤 "번역 실패 · 다시 시도"(수동).
- 실시간 메시지의 폴백: 원문 수신 후 15초 안에 내 언어 번역이 안 왔고 `chat:translation`의 `translations:{}`(대상 없음)도 안 왔으면 배치 후보에 넣는다.
- 한도. 배치는 사용자당 20회/분. 단건 `/translate`(게시글)는 기존 60/10 유지. 서버 주도 호출은 전역 큐(동시 4, `TRANSLATE_GLOBAL_RPM` 기본 120)로 상한.

### 3.6 데이터 — `message_translations` 테이블 (I)

```sql
-- 005_message_translations.sql
CREATE TABLE IF NOT EXISTS message_translations (
  message_id INT NOT NULL,
  lang VARCHAR(8) NOT NULL,
  text TEXT NOT NULL,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (message_id, lang),
  CONSTRAINT fk_message_translations_message FOREIGN KEY (message_id) REFERENCES messages(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

엔티티 `MessageTranslation`을 `app.module.ts` 엔티티 목록에 추가한다. 보존 정리(retention)는 FK CASCADE로 함께 지워진다. dev `synchronize`가 켜져 있으면 엔티티와 SQL이 같은 정의여야 한다(인덱스·타입 일치 테스트).

### 3.7 계약 (서버 ↔ 웹) — 공유 픽스처 `docs/contracts/chat-events.json`

| 이름 | 방향 | 페이로드 |
|---|---|---|
| `chat:language` | C→S | `{ lang: 'ko'\|'en'\|'ja'\|'zh'\|'ru'\|null }` — 접속 직후·UI 언어 변경·자동번역 토글 때 |
| `chat:message` (요청) | C→S | `content: string`, ack `{ ok: true } \| { ok: false, reason: 'invalid'\|'rate_limit'\|'failed' }` |
| `chat:message` (방송) | S→C | `{ id: number, nickname, allianceName: string\|null, language, content, createdAt: ISO string }` (지금과 같음) |
| `chat:translation` | S→C | `{ id: number, translations: { [lang]: string }, failed?: lang[], error?: 'provider'\|'limit' }` — 대상 0이면 `translations: {}` |
| `chat:history` | S→C | 항목에 `translations: { [lang]: string }` 추가(없으면 `{}`) |
| `chat:system` | S→C | `{ kind: 'history_error' }` 등 **구조화 객체**. 입퇴장 방송은 제거(C-5) — 웹이 `online:updated` diff로 만든다 |
| `online:updated` | S→C | 변경 없음 `Array<{ nickname, alliance, role }>` |
| `POST /translate/batch` | C→S | 3.5 참조. 429는 `{ retryAfterMs }` |
| `POST /translate` | C→S | 변경 없음(게시글) |
| `GET /translate/usage` | C→S | developer 전용 `{ calls, inputTokens, cachedTokens, outputTokens, totalMs, since }` |
| `GET /translations/:key` | — | **삭제**(C-12) |

계약 픽스처는 서버 spec이 emit 페이로드를 JSON 왕복시켜 픽스처와 대조하고, 웹 spec이 같은 픽스처를 핸들러에 넣는다(C-13).

### 3.8 웹 구조

- store. 메시지 객체는 지금 필드 그대로 두고, **번역은 별도 맵** `chatTranslations: { [id: number]: { [lang]: string } }`에 둔다(B — 도착 순서·재연결·히스토리 재수신에 무관). 액션 `mergeChatTranslations(id, map)`, `setChatTranslationsBulk(entries)`. `translatedContent`·`translatedLanguage`·`setChatMessageTranslation`은 삭제. 실패 집합 `chatTranslationFailed: { [id]: true }`.
- 표시 셀렉터 `selectDisplay(message, translations, myLang, autoTranslate)` → `{ text, state: 'original'|'translated'|'pending'|'failed'|'none' }`(순수 함수, `web/src/chat/display.js`).
- 동기화 모듈 `web/src/chat/translationSync.js`(순수 함수 + 작은 상태). 책임 — `chat:translation` 적용, 히스토리 최신 50건 배치·스크롤 시 추가 배치, 15초 푸시 대기 후 폴백, `failed` 재시도(10초·30초), 언어 변경·재연결 시 리셋, `chat:language` 송신 요청. 상태 기계는 테스트로 고정한다.
- 웹 localStorage 번역 캐시는 **채팅에서 제거**한다(M). 게시글 캐시는 키 버전을 `v3`로 올려 유지.
- 시스템 메시지. `online:updated` 이전 목록과의 diff로 입장·퇴장을 만들어 i18n 문구로 표시하고, 2초 안에 여러 건이면 "N명 입장·M명 퇴장" 한 줄로 합친다. 서버 `chat:system`은 `{ kind }` 객체를 i18n 키로 바꿔 표시.
- 스토어 상한에서 밀린 메시지는 번역 대상에서 제외(C-3).
- 언어 초기화 규칙 통일(C-11). 로그인(hydrate) 시 localStorage `wos-lang`이 없을 때만 계정 언어로 설정. 메인 App과 동화 버전 둘 다.
- 헤더 언어 셀렉트에 `ru` 추가. UI 문구는 `UI_TEXTS[lang] ?? UI_TEXTS.en` 폴백(C-7).
- 컴포넌트. `ChatTab`·`ChatDock`의 메시지 항목·연맹 색·시간 포맷을 `ChatMessageItem.jsx`, `chatFormat.js`로 합친다. 작전판 채팅 패널과 동화 버전이 같은 컴포넌트를 쓴다.

### 3.9 UI/UX (테마 3종 안에서)

- 번역 상태. 내 언어 번역이 없는 외국어 메시지는 원문 아래에 작은 "번역 중…"(`aria-live="polite"`). 실패가 확정되면 "번역 실패 · 다시 시도" `<button>`. 번역이 오면 번역문을 본문으로, "원문 보기" 토글은 지금처럼. 자동번역 off면 원문만, 상태 없음.
- 375px에서 입력창·전송 버튼·온라인 스트립·토글이 겹치지 않게. 스크롤은 사용자가 바닥에 있을 때만 자동 고정, 위로 올려 읽는 중이면 "새 메시지 N" 배지.
- 접근성. 토글 `aria-pressed`, 버튼은 `<button>`.
- 세 테마 모두 같은 선택자를 갖게 하고 daylight 스코프에 빠진 채팅 규칙을 채운다.

## 4. 비용 모델 (감사 C 6절 공식)

접속자 N, 언어 수 L, 분당 메시지 M, 용어 행 평균 g≈3, 원문 평균 30~60토큰.

- 현재. 웹 요청 수요 M×N×(L−1)/L(N=100, L=4, M=30이면 2,250건/분)인데 웹이 낼 수 있는 양은 N×9.2=923건/분이라 백로그가 쌓이고, 서버 공급자 호출 M×D≈90/분이 전역 60을 넘는다.
- v2. 공급자 호출 = M(메시지당 1회, N·L 무관) = 30/분. 입력 ≈ 80(규칙)+15g+20(입력 포장)+원문 ≈ 170토큰, 출력 ≈ D×24+20 ≈ 92토큰. 용어집 전체 주입(≈440토큰) 대비 입력 61% 절감, 일당(43,200건) 1,170만 토큰 절감. 늦은 접속 배치는 "최신 50건 + 스크롤 시"로 접속 순간 폭주를 막는다.

## 5. 반증 — 이 설계가 틀릴 조건

- 접속자 언어 집합에 없던 언어 사용자가 나중에 접속하면 그 언어 번역은 배치 경로로 나중에 생긴다. 지연은 있지만 결손은 없다.
- 스크립트 판별은 한글·가나·키릴 단일 스크립트에서만 건너뛴다. 라틴·한자·혼합은 모델의 `source` 판단에 맡기므로 호출 1회는 든다.
- 다중 대상 JSON에서 모델이 한 언어를 비우면 그 언어만 `failed`로 방송하고 배치 경로가 메운다.
- 전역 120/분을 넘는 폭주에는 `error:'limit'` 방송 뒤 배치 경로가 뒤따라 메운다. 폭주 시 비용 상한이 곧 품질 상한이다.
- `message_translations`는 메시지 보존 정리와 함께 지워진다. 게시글 번역은 텍스트 해시 캐시라 원문 언어 모호성이 남는다(게시글은 단일 언어 게시판이라 실질 영향 낮음).
